前几天有用户反映站里刷新、发嘟文都卡卡的。本以为是一次常规的性能排查，没想到一路挖下去，挖出了数据库膨胀、被超时废掉的清理任务、一批假备份，最后顺手 ban 了一波垃圾账号。整个过程值得记下来，给自建 Mastodon 的朋友做个参考。

本站环境：Docker 部署（web / sidekiq×3 / streaming / PostgreSQL 14 / Redis / ES），12 核 47G 内存，数据库 36GB。

## 一、先抓现行

上手先看资源：负载 3-4（12 核，不算高），内存充足，磁盘充足。但 `docker stats` 里 DB 容器 CPU 却跑到 180%，很不正常。

进数据库查 `pg_stat_activity`，一条 `COPY public.statuses (...)` 已经跑了 7 分多钟，来源是 `pg_dump`。某个脚本在 20:44 晚高峰触发了一次 36GB 的全量备份，跑了 25 分钟左右。

数据印证了影响：

| 时段       | p50   | p99    | 最慢    |
| -------- | ----- | ------ | ----- |
| dump 期间  | 148ms | 2243ms | 34.8s |
| dump 结束后 | 51ms  | 959ms  | 2s    |

dump 一停，响应立刻回落。但这解释不了“最近一直卡”，继续挖。

## 二、慢性问题：数据库的三个老毛病

慢请求日志里，`/api/v1/accounts/*/statuses`、`/api/v2/notifications` 这类接口的 db 耗时动辄 2-5 秒。瓶颈在数据库，具体是三个问题叠加：

1. 表膨胀严重，autovacuum 一直没干活。`statuses` 表 17GB / 2100 万行，挂着 130 万死元组；`preview_cards` 死元组占比 44%，`mentions` 36%。而这些表上一次 autovacuum 的时间是空的，从来没被清过。原因是默认阈值 `autovacuum_vacuum_scale_factor = 0.2`：对 2100 万行的表，要攒够 420 万死元组才触发，永远达不到。

2. 统计信息严重失真。VACUUM 时发现 `mentions` 的行数估计是 35 万，实际约 900 万；`preview_cards` 估计 10.9 万，实际 340 万。查询规划器一直拿着错误的行数选执行计划，慢查询有它一份功劳。

3. 每晚的清理任务在被超时悄悄杀掉。DB 日志里凌晨 3 点反复出现 `canceling statement due to statement timeout`。`mastodon` 角色设了 `statement_timeout = 60s`，而 cron 里 `tootctl statuses remove --days=90` 的批量 DELETE 经常超过 60 秒，被杀、重试、再被杀。旧嘟文清不动，表越滚越大，恶性循环。

## 三、假备份

排查中顺手看了眼 `backups/` 目录，6 月底以来的 10 个“预部署备份”居然全是 1017 字节，一个空库的 pg\_dump 体积。

对比脚本历史版本发现，旧版 `deploy.sh` 里写的是：

```bash
pg_dump -Fc -U postgres postgres        # 导的是 postgres 空库！
# 而不是
pg_dump -Fc -U postgres mastodon_production
```

也就是说这段时间的每次部署，“备份”都是假的，而脚本的 `[ -s file ]` 检查（非空即通过）完全防不住。万幸每天凌晨 4 点上传 S3 的备份脚本用的是正确的库名，当天 6.87GB 备份成功，安全垫一直在正常工作。

修复办法：改对库名，备份后校验文件不足 100MB 立即中止部署，自动只保留最近 3 份（每份约 7GB，防止磁盘无限涨）。

## 四、修复与效果

低峰期依次执行：

1. 8 张膨胀表 `VACUUM (ANALYZE)`，死元组从合计 386 万清到接近 0，统计信息全部修正（全程约 8 分钟，在线操作不锁表）；
2. 按表调低 autovacuum 阈值，例如 `statuses` 改为 `scale_factor = 0.02 + threshold = 10000`（约 43 万死元组即触发）；
3. cron 里三个清理任务加 `PGOPTIONS='-c statement_timeout=0'` 绕过角色超时；
4. 手动补跑一次清理，删掉 51.3 万个过期会话，`statuses` 表 17GB → 15GB；
5. 6 个膨胀索引 `REINDEX CONCURRENTLY`：`index_statuses_on_uri` 从 2733MB 瘦到 1768MB，合计回收约 1.9GB。

最终效果：

| 指标  | 治理前（6小时窗口） | 治理后   |
| --- | ---------- | ----- |
| p50 | 184ms      | 25ms  |
| p99 | 5147ms     | 823ms |

## 五、顺手大扫除：50G 垃圾

`/home/mastodon` 目录积攒了三年的杂物，一次清掉约 50G：

* PG12 时代的旧数据目录和归档（27G + 4.4G，2023 年迁移 PG14 后就该删）；

* 16G 的 2025 年老 dump、2023 年的 zip 和 tar.gz 快照；

* 一批 0 字节 / 1KB 的废备份。

留下的东西归类为 `backups/`（部署备份）、`archive/`（旧配置）、`scripts/`（运维脚本），磁盘使用率从 23% 降到 12%。

## 六、728 个垃圾账号

目录里翻出一个 2024 年写的反垃圾脚本 `kill-spam.py`，已经坏得不能用了：数据库 IP 写死（容器重建后早变了）、API token 已被删除。修复后扫了一遍全库，特征是：

```
用户名恰好 10 位小写字母+数字（机器生成感）
+ 显示名为空或同用户名
+ 无头像
+ 2024-02-15 后注册
+ 远程账号、未冻结、来源实例未被封
```

命中 728 个账号，分布很说明问题：kitsui.life（56 个）、seda.social（34 个）等小实例在 2024 年 10-11 月的注册潮，典型垃圾号特征。

处理时做了两个安全设计：

* 账号级全自动（举报+冻结，可逆），但域名级 silence 加一道保险：本地用户关注数 ≥3 的实例自动跳过。728 个疑似里混着 mastodon.social（115 个）、misskey.io 等正常大站的账号，没有这道保险就会把大站整个 silence 掉，联邦时间线直接瘫痪；

* 不用 HTTP API 逐条调（限速 300 次/5 分钟，要跑近一小时），改成在 web 容器里 `rails runner` 直接调官方 Service，几分钟完事。

也有翻车时刻：第一版脚本把 `Admin::AccountAction` 的方法名写成了 `.call`（实际是 `.save!`），导致 728 条举报全部成功、冻结全部失败。发现后按已有举报补跑冻结，全部处理完毕，举报自动结案。

最终结果：728 个垃圾账号全部冻结，100 个垃圾实例被 silence，28 个正常实例受保护零误伤，站点响应保持在 0.2s 以内。

## 七、总结

1. 备份不验证等于没备份。一个非空检查让 1KB 的假备份蒙混过关小半年。备份脚本必须校验“像不像真的”：大小、格式，最好定期做一次恢复演练。
2. autovacuum 默认值不适合大表。表越大，scale factor 越要调小，否则死元组永远攒不到触发线。
3. statement\_timeout 会悄悄废掉维护任务。应用角色设了超时，批量清理这种长任务要么单独豁免，要么换通道执行。
4. 大操作避开高峰。一次 36GB 的全量 dump 就足以让全站卡 25 分钟。
5. 运维脚本也是代码，也会腐烂。写死的容器 IP、会过期的 token，都会随时间失效。定期检查工具本身，和检查服务一样重要。
